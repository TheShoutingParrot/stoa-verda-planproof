# Pre-registered scan-next comparison on 72 reserved test drawings

This protocol fixes the next before/after measurement of the local scan reader before anyone sees a result. The reference arm is the reader at commit `b948d6744548417b7a037f32b9317c830ea7e52e`, the version that returned 167 exact counts on 398 prompts in the [48-drawing comparison](scan-revision-evaluation.md). The after arm is the single candidate revision pinned in the script as `AFTER_REVISION` (see the addendum). Both arms read the same 72 original CubiCasa5K PNGs and the same 608 released English count prompts through `scripts.scan_reader.run`, with a blank hosted endpoint and no key. The cohort was frozen and the reference arm was sealed twice before any implementation work was evaluated. No sponsor answer, unit or vector annotation for these drawings was opened to choose them or to run the reference arm. The drawings were not inspected or used in any development round; an automated release-wide bedroom gate opened 40 of them on 2026-11-13 (see the audit paragraph). ## Arms and seals

Each arm loads the reader from a snapshot of a Git revision under `.local/evaluation/scan-next/<arm>/src/`, never from working files. The snapshot follows the reader’s imports of product modules. For an after arm it also copies every tracked non-Python file under `scripts/` and any file passed with `--source`. The run step drops the harness directory from the import path and refuses to continue if any reader module loads from outside the snapshot. It reads staged PNGs only and receives no archive path. It forbids hosted calls by replacing the hosted client with an error, blocks socket connections and name lookups during inference, and refuses to start if `NEMOTRON_BASE_URL` or `NEMOTRON_API_KEY` is set. A hand-off to the hosted model therefore becomes a deferral. Outputs are written one prompt at a time and resume only with an identical configuration.

The configuration records the per-file source digests, the revision, the manifest digest, the detector source digests, the weight digest, the detector revision, the Python, macOS, package and Tesseract versions and the device. The seal records the digests of the configuration, the predictions (a map from prompt ID to record, serialised as canonical JSON with sorted keys) and the manifest, the per-file source digests and their combined digest. It is written once, after the last prompt, and every later command recomputes it from the files before use. Sealed outputs are read-only. Scoring requires the two arms to share weights, detector source, detector revision, environment, network setting and manifest.

The baseline arm `before` is pinned to `b948d67`. Its seven snapshot files have the same digests as the sources recorded in `.local/evaluation/scan-revision/new/config.json`, the reader that produced 167 of 398, so it is the published reader. Their combined digest is `9e5bc7772a72c25e7435f31d779913e73335a63a0c3b6f5239f47ccfb94de54d`.

The baseline ran on 2026-11-14 on the Apple M5 GPU (MPS) with Python 3.12.13, torch 2.15.0, numpy 2.5.4, Pillow 13.0.0, opencv-python-headless 5.0.0.93, Tesseract 5.5.3 and macOS 26.5.1, with the detector weights `dd20b4e1bf1d670f2125107b079df06958b1ccd36e49a464ab739aeb00b8e7a2` at upstream revision `c34440266665a11f4484eb06cd2e4b7d72ad76c1`. It took 854 seconds for 608 prompts. Its configuration digest is `bc9b120e654b3f2b3e734835805cd3beef768de0839ec9ee79b1a7ec43c4f7d6`, its predictions digest is `b5523194532929d32e2d56c61ad98d9518a755f8010fedd63a720e017deadd6e`, and the canonical digest of its seal is `412ddb3f9ea6297ce8d81a26ff45a320167a7b2ed4662a28b73395f9f8767a3a`. The same reader then ran again into a separate arm, `before-repeat`, with an identical configuration (seal `6310e14408bbdc47163919f5df241dabf7b79982d3647b7ef08fedef97bab2ca`). The two runs differed in no answer, no status, no method and no evidence list on any of the 608 prompts. Their prediction digests differ only because each record keeps its own elapsed time. Only structure was checked before scoring: every seal, every record’s schema and status, and the coverage of the manifest. No count, coverage or distribution of the baseline was summarised.

## Endpoints

Scoring opens the sponsor question file only after both seals verify, and it keeps answers for the 608 frozen rows only. A count is exact only when the arm answered and the integer equals the sponsor answer. A deferral counts in every denominator and is never treated as zero. Zero is a numeric answer.

**Primary endpoint.** The paired difference in exact accuracy over all 608 frozen prompts, after minus before, in percentage points. Its 95% interval comes from 10,000 bootstrap resamples of whole drawings within each style, keeping every prompt of a drawing together, with the seed string above plus `-bootstrap`. The round shows a measured improvement only if the lower end of this interval is above zero. The repeat-run agreement above says how large a difference the reader’s own variation can produce.

**Secondary endpoints.** For each arm: exact, wrong and deferred counts, coverage, and accuracy among answered prompts. These are reported overall, by family group, by family, by style, for the comparable eleven-family subset and as an equal-style-weighted exact accuracy, the mean of the two style accuracies. The figure to set beside the 24 + 24 cohort is the equal-style-weighted exact accuracy on the comparable eleven families (see the addendum). The family groups are objects (doors, windows, toilet bowls, sinks, showers; 333 prompts), rooms (bedrooms, saunas, kitchens, bathrooms, separate WC rooms, balconies; 203) and storeys (floors; 72). Paired gains and losses, newly answered prompts and mean absolute error on prompts both arms answered are reported for every block, and the clustered interval is reported for every block as a description.

**Per-track readout.** Track 1 is doors and windows (123 prompts). Track 2 is rooms, storeys and showers (341 prompts). Toilet bowls and sinks (144 prompts) belong to neither track and are reported as an untouched control. Each track reports the same paired block. Track intervals are descriptive; only the primary endpoint carries a claim.

**Regressions.** The score lists every regression, a prompt that was exact before and not exact after, and every newly wrong prompt, deferred before and wrong after, with its ID, drawing, family, question, sponsor count and both arms’ status and answer. Gains are listed the same way.

**Localization.** After scoring, `scripts/score_scan_evidence.py` compares the marks on door, window, toilet-bowl and sink prompts with the original CubiCasa5K vector annotations at IoU 0.25, one mark per annotated object. It reports marks matched over marks placed, annotated objects located, and questions with every object marked and no extra mark, per class and in total. It checks each upstream original PNG against the frozen image digest.

## Addendum of 2026-11-14: rules fixed before the after run

This addendum was written on 2026-11-14 by the independent evaluator, after the audit of the freeze, seals and harness (findings E1 to E9) and the hygiene audit (finding H1), and before any after-arm inference. At the time of writing no after, after-repeat or before-control arm had run on the frozen cohort, nothing had been scored, and no sponsor answer, unit, annotation or per-drawing prediction of a frozen drawing had been opened. It fixes every remaining decision so that none is left until results are visible. Where it differs from the text above, the addendum governs.

The sealed arms and the manifest are untouched. The canonical seal digests of `before` (`412ddb3f9ea6297ce8d81a26ff45a320167a7b2ed4662a28b73395f9f8767a3a`) and `before-repeat` (`6310e14408bbdc47163919f5df241dabf7b79982d3647b7ef08fedef97bab2ca`) are now pinned in the script as `BASELINE_SEALS`, beside the manifest `FINGERPRINT`. `verify` fails for either arm when its seal differs and the work directory is the default one or the manifest is the frozen one, and `run` refuses to recreate a missing pinned baseline arm.

**R1. Arms and roles.** Five arm names can run and no other. `before` and `before-repeat` are the two sealed baseline runs. `before-control` is a third run of the baseline reader, pinned like them to `b948d67` and to the source fingerprint above. `after` and `after-repeat` are two runs of the candidate pinned in the script as `AFTER_REVISION`. That constant is unset now. Phase B sets it to the frozen candidate’s full SHA in one commit before any after arm runs, and the harness refuses any other revision for both after arms. The sealed `before` stays the comparator of the primary endpoint. `after`, in its first valid run under R4, is the scored arm whatever the repeat shows. No other revision is run or scored on this cohort.

**R2. Order and run conditions.** The three new arms run in the order `before-control`, `after`, `after-repeat`, back to back under one GPU lock, with no other agent job running on the machine. Each arm starts once the 1-minute load average is below 12, waiting at most 30 minutes, and then proceeds regardless. Each run session appends to `<arm>/conditions.json` the load wait, `uptime` and the load averages at start and end, the wall time, the number of prompts already sealed and the harness file digest and commit. Per-prompt elapsed time stays in each record. A resume after an interruption is the same run and adds a session. Every session start, seal and set-aside is also appended to `run-history.jsonl` in the work directory, outside the arm directories, and `score` copies it into the summary, so an arm that was deleted and run again outside R4 stays visible and is reported as a deviation.

**R3. Time-out log.** Each macOS Vision or Tesseract call of the readers has a time limit (20 s; 5 s for the Tesseract language list). When one expires, the reader goes on with less text and can defer or miscount, and it reports nothing. During inference the harness now wraps `subprocess.run` in a pass-through that records each `subprocess.TimeoutExpired` (program, limit, time, prompt index in manifest order, prompt ID and drawing index) in `<arm>/timeouts.json` and re-raises the same exception unchanged. The reader code is not modified. `run` and `verify` print the count. For new arms the seal also covers `timeouts.json` and `conditions.json`.

**R4. Validity rule for time-outs.** A run of any new arm that logs one or more time-outs is set aside unseen. `settle --arm <arm>` renames it `<arm>.set-aside` without opening any answer, keeps it for audit and never scores it. The arm is then run again from scratch once, straight away and before the next arm. If the second run also logs time-outs, the run with fewer time-outs stands; on a tie the first run stands. The count and the affected prompt IDs of the standing run are reported. `settle` records this in `settle-<arm>.json`, and `score` refuses an arm with logged time-outs that has not been through it. The two sealed baseline runs predate the log. Their slowest room or storey prompts took 17.5 s and 11.4 s, below the 20 s limit, and they agree on all 608 records.

**R5. Reader exceptions and invalid reports.** A prompt on which the reader raises, or returns a report that fails `nemotron.parse_count`, is recorded as a deferral with status `abstained`, method `reader_error` or `invalid_report` and the exception type and message cut to 220 characters as the reason. It counts in every denominator, is never exact, is counted by `verify` and is listed by `score` under `harness_deferrals`. One bad report does not abort or unseal an arm. A network or hosted call still aborts the run, because it breaks the protocol. Two checks of the product (`scan_library._safe_report`) also apply now: an answered report must carry the coordinate system `xyxy_top_left_0_to_1000`, and an answered zero that carries coverage evidence must pass the same evidence check. Either check can only turn an answer into a deferral. They apply to the three new arms. The sealed `before` arm was normalised without them, so any effect on the baseline reader shows up as a difference between `before` and `before-control` and brings in R7. On the authors’ 1,695 development room-map answers neither check changes an answer (audit E6).

**R6. One scoring.** `score` refuses a before arm other than `before`, an after arm other than `after`, an after arm not at `AFTER_REVISION`, and any run before `before-control` and `after-repeat` are sealed, paired with `before` and settled under R4. It appends each scoring to `scorings.json` before the sponsor answers are opened, refuses a second scoring unless `--rescore` is given, and lists every scoring in the summary. The reported result is the first scoring.

**R7. Noise floors and the claim.** `noise --arms before before-control` and `noise --arms after after-repeat` write `noise-<arm1>-<arm2>.json` with the numbers of prompts whose answer, status, evidence list or method differs. Both are reported as noise floors. If `before-control` differs from `before` in any answer (status or count), the primary endpoint is reported against both, and an improvement is claimed only if the lower end of the interval is above zero against both. `score` applies this rule and writes it as `claim.improvement_shown`, with `primary_endpoint_against_before_control` beside the primary endpoint. The repeat of the after arm never changes which run is scored.

**R8. Timing.** Any timing statement compares `before-control` with `after`, which run back to back under recorded conditions (`timing` in the summary). The sealed `before` arm is never a timing reference, because load slowed it three to five times against the authors’ measurements.

**R9. The like-for-like figure.** The summary adds `comparable_equal_style_weighted_exact_accuracy`, the mean of the two style accuracies over the eleven families of the 398-prompt comparison, with its paired difference in points. This is the figure to set beside the 24 + 24 cohort. The pooled accuracy over 608 prompts is expected to be lower than the earlier cohort’s for reasons of composition alone: 84% of the prompts (512 of 608) are on architectural drawings, against 48% before, and the 66 shower prompts, which no reader answers at either revision, count as deferrals. With the baseline reader’s per-style accuracies on the earlier cohort, composition alone predicts about 31% pooled over 608 prompts, about 37% for the equal-style figure over 608 and about 41.5% for the comparable equal-style figure (audit E4). The figure is descriptive. The primary endpoint is unchanged.

**R10. Sensitivity to the bedroom gate.** The hygiene audit (H1) found that an automated release-wide bedroom gate on 2026-11-13 opened 129 reserved drawings, 40 of them in this cohort. The summary reports the primary endpoint and the exact, wrong and deferred counts separately for the 40 frozen drawings with a gate file and the 32 without (`gate_sensitivity`). Membership comes from the file names under `.local/evaluation/full-english/finnish/gates/` only and is pinned by count and digest (`GATE_MEMBERS`). No gate file and no row of the gate table is opened. This split is descriptive and carries no claim.

**R11. Run time.** Each arm’s time depends strongly on load. The sealed baseline runs took 854 s and 1,011 s for 72 drawings at a load average of 10 to 15. In the rehearsal on six exposed drawings the baseline reader took 8 s per drawing at a load of about 20 and 37 s per drawing at 25 to 35, and the candidate 37 to 57 s per drawing at 30 to 38. The audit measured 50 s and 100 s per drawing at about 40. For 72 drawings, plan about 10 to 15 minutes for `before-control` and 15 to 30 minutes for each after arm at a load below 12, and up to an hour for `before-control` and up to two hours for each after arm at a load near 40, plus at most 30 minutes of load wait per arm. These are estimates, not rules.

**Harness changes made after the baseline was sealed.** All are on the branch `scan-next/evaluation-hardened`, after `9c78db3`: reader exceptions and invalid reports as recorded deferrals, with the two product checks (R5); pinned baseline seals and per-pair noise files (E5); `AFTER_REVISION`, the five arm names and a single scoring (R1, R6); `before-control`, the time-out log, run conditions, the load wait and `settle` (R2 to R4, R7, R8); the comparable equal-style figure (R9); the gate-record split (R10); the run history (R2); scoring without a `before-repeat` arm in a rehearsal directory; a unit test that accepts a pinned `AFTER_REVISION`; and `scripts/scan_next_arms.sh`, which runs the three new arms in order under R4. None changes how a reader answers a prompt. None changes the seal of an arm without `timeouts.json` and `conditions.json`, so the two sealed baseline arms verify with the same digests as before.

**Text corrections in this commit.** The title and the opening paragraph no longer call the drawings fresh. They say the drawings were not inspected or used in any development round and add the gate fact. The opening paragraph now names the single pinned after revision. The audit paragraph says what the gate table holds. The seal sentence describes the predictions digest correctly: it is over a map from prompt ID to record, serialised with sorted keys, not over the predictions in manifest order. The comparison sentence names the comparable equal-style figure. The per-track paragraph says track intervals are descriptive. The runbook below replaces the earlier one, including its time estimate.

## Runbook for phase B

Run these in order from a fresh worktree of the branch `scan-next/evaluation-hardened`, with the shared `.local` directory linked and the sponsor ZIP at its default path. `<CANDIDATE_SHA>` is the only parameter: the full 40-character SHA of the frozen candidate. Stop at the first command that fails. The baseline arms stay as they are.

```sh
C=<CANDIDATE_SHA>
PY=.local/scan-dev/objects/venv/bin/python
GPU=.local/scan-next/with-gpu
H="python3 scripts/benchmark_scan_next.py"
W=.local/evaluation/scan-next
D=.local/scan-next/evaluator-c/dry                 # scratch for the dry rehearsal (exposed drawings only)
DM=.local/scan-next/evaluator-b/dry-manifest.json  # six exposed drawings of the 48-drawing cohort
DRY="$PY -B .local/scan-next/evaluator-b/tools/dry.py $PWD"
unset NEMOTRON_BASE_URL NEMOTRON_API_KEY

# 1. Pin the candidate in one commit (R1)
test "$(git rev-parse --verify "$C^{commit}")" = "$C"
sed -i '' "s/^AFTER_REVISION = None$/AFTER_REVISION = \"$C\"/" scripts/benchmark_scan_next.py
git diff --stat                                    # exactly one line in scripts/benchmark_scan_next.py
$PY -B -m unittest tests.test_scan_next
git commit -am "Pin the scan-next after arms to the frozen candidate"   # plus the trailer line

# 2. Structure checks of the sealed baseline (pinned digests)
$H verify --arm before
$H verify --arm before-repeat

# 3. Dry rehearsal of the final commit on six exposed drawings, with the committed pin
mkdir -p $D
$DRY prepare --manifest $DM --work $D
$GPU /bin/sh -c "$DRY run --arm before --manifest $DM --work $D --load-wait 0 && \
  $DRY run --arm after --revision $C --manifest $DM --work $D --load-wait 0" > $D/../dry-run.log 2>&1
$DRY verify --arm after --manifest $DM --work $D
python3 .local/scan-next/review/evaluation-review/tools/dry_after_checks.py $D before after

# 4. Leak check of the candidate, the implementers' and the reviewers' directories: must exit 0
$H leak-check --revision $C \
  --scratch .local/scan-next/openings --scratch .local/scan-next/deferred \
  --scratch .local/scan-next/integration --scratch .local/scan-next/review \
  --scratch .claude/worktrees/wf_6b7c1a21-971-1 --scratch .claude/worktrees/wf_6b7c1a21-971-2 \
  --scratch .claude/worktrees/wf_0803653c-007-1 --scratch .claude/worktrees/wf_0803653c-007-2

# 5. The three new arms back to back under one GPU lock, nothing else running (R2, R4)
$GPU /bin/sh scripts/scan_next_arms.sh $C

# 6. Structure and agreement checks; no answer is opened
$H verify --arm before-control
$H verify --arm after
$H verify --arm after-repeat
$H noise --arms before before-control
$H noise --arms after after-repeat

# 7. Leak check again: repeat step 4

# 8. Score once; only now are sponsor answers read (R6, R7)
$H score --report docs/scan-next-results-$(date +%Y-%m-%d).json

# 9. Annotations from the public archive (network), localization, replay bundle and links
$H fetch-refs
uv run --no-project --python 3.12 --with svgpathtools==1.8.0 python scripts/benchmark_scan_next.py localize
$H example --limit 3
```

Step 3 must show both dry arms sealed with zero harness deferrals, `local_room_layout` answers on room and storey prompts and a second door and window reading. At `71a01e3` the rehearsal gave the figures in the rehearsal note below; a final commit with no reader change after `71a01e3` should give the same. Step 5 writes `arms.log`, `<arm>-run-<n>.log`, `settle-<arm>.json` and, for a run set aside under R4, `<arm>.set-aside` in the work directory. If a step fails, stop and record why; do not edit the harness or rerun an arm outside R4.

To repeat the scorer validation, write its output to a scratch directory: `uv run --no-project --python 3.12 --with svgpathtools==1.8.0 python scripts/benchmark_scan_next.py validate --references .local/scan-dev/revision-scoring/references.zip --work <scratch>`.

The leak check fails if any frozen drawing name, in sponsor, upstream or URL-encoded form, or any frozen image digest appears in a tracked file of the candidate revision, in any blob of a commit between `b948d67` and the candidate, or in a file name, file, ZIP member name or symlink target under the directories passed with `--scratch` (by default `.local/scan-next/openings` and `.local/scan-next/deferred`; step 4 adds the integration and review directories and the implementers’ and reviewers’ worktrees). A file byte-identical to a frozen PNG also fails it. The frozen manifest itself is allowed only at its exact digest. A resized or cropped copy of a fresh PNG would not be detected by this check. It writes its findings to `.local/evaluation/scan-next/leak-check-<commit>.json`. If the reader at `<commit>` reads a data file outside `scripts/`, pass it with `--source`; otherwise the snapshot will not contain it.

`score` writes `.local/evaluation/scan-next/scorings.json`, `paired-rows.json` and `summary.json`. In the paired rows `old` is the before arm and `new` is the after arm. `fetch-refs` refuses to run until the before and after arms are sealed. It reuses the cached central directory of the public archive at `.local/scan-dev/grounding/central` when its digest matches, takes each original PNG from the sponsor ZIP when its CRC matches the upstream member, downloads `model.svg` and `F1_scaled.png` for each drawing with a door, window, toilet-bowl or sink prompt by HTTP range requests from `https://zenodo.org/api/records/2613548/files/cubicasa5k.zip/content`, and writes `.local/evaluation/scan-next/references/references.zip`. `localize` writes `grounding.json` and `localization.json`.

`example` writes `.local/evaluation/scan-next/scan-next-replay.json`, a replay bundle in the format of `scripts/export_scan_replay.py`, and prints its SHA-256 with links of the form `http://127.0.0.1:4179/scan-drawing.html?path=data%2Fcubicasa5k%2F<drawing>.png&question=<question>` for up to three prompts the after arm gained, track prompts first. The library page reads only replay bundles registered in `scripts/scan_library.py` with their digest. To make a link open the sealed answer, copy the bundle to `public/data/finnish/scan-next-replay.json` and register it beside `REVISION_REPLAY_FILE` in a product commit. Without that change, start `python3 server.py` with the specialist Python at the after revision, open the link and choose **Run count**.

## Rehearsal note (2026-11-14, exposed drawings only)

The whole sequence was rehearsed with the hardened harness on the six exposed drawings of the audit’s dry manifest (60 prompts, all from the 48-drawing cohort), in a scratch work directory, with the lead’s then-current commit `71a01e3` standing in for the candidate through a test override (never in the committed `AFTER_REVISION`). The arms `before`, `before-control`, `after` and `after-repeat` sealed with zero harness deferrals.
